案件の進め方

新しい案件が入ったら、この6工程を順番に進めます。お客様に公開している 開発体制・品質管理 と同じ流れです。

01ヒアリング
課題整理 02要件定義
設計 03見積
契約 04開発
検証 05移行
本番 06保守
改善

1枚でわかる流れ

工程 やること 次に進む合図
01 ヒアリング 困っていることを聞き、第1段階の範囲を切る 受ける / 待つ / やめる を書いた
02 要件定義 画面・データ・権限・連携・非機能を文書にする 完了定義が、誰が読んでも同じ意味になる
03 見積・契約 内訳を積み、前提と除外を書く 発注か契約の事実がある
04 開発・検証 デザインと開発を同時に進め、初稿 → 修正 → テスト お客様が操作して合格にした記録がある
05 移行・本番 データと権限を入れ、現場に渡す 本番で仕事が回っている
06 保守・改善 壊れの対応と、新しい機能を分ける 窓口と、保守に含む範囲が決まっている

キックオフMTGは 02 要件定義の入口、検収は 04 開発・検証の出口として扱います。工程は増やしません。お客様への説明と社内の手順を同じにするためです。

いつ何を確定させるか

あとで動くと後戻りが大きいものから順に確定させます。ここが決まっていないまま先へ進めると、作り直しになります。

タイミング ここで確定させるもの
キックオフMTG 目的とゴール、対象ユーザーの種別、管理画面の数、権限の数、機能のカテゴリ、外部連携の有無
要件定義 管理画面構成、権限・ロール定義、機能一覧、機能ごとの大枠フロー、サイトマップ、画面遷移
初稿提出 デザイン、レイアウト構成、リンク先、カラー、フォント、アニメーション・エフェクトの有無
修正・改善 不具合、表示崩れ、文言や改行、画像の差し替え、動きの大枠
動作テスト・検収 残りの不具合、アニメーション・エフェクトの動き
リリース・引き渡し デバッグを終えて、正式に稼働開始。保守運用に入るかを決める

うちの進め方の特徴

内部ライブラリがある

認証・権限管理・管理画面は保有しているものを使います。規模が大きいほど、スピードと金額で差が出ます。

デザインと開発を同時に

「UIが決まらないと実装できない」の順番に縛られません。中身から先に作れる分だけ短くなります。

資料を見えるところに

議事録・仕様書・操作方法をWebページにして共有します。認識のずれによる後戻りを消します。

使うツール

04 開発・検証 から先は、5つのツールを行き来します。ローカルとクラウドの分け方を先に押さえると、どこを見ればいいか迷いません。

① Cursor ローカル / コードを書く・編集する ② GitHub Desktop ローカル / 変更を保存してクラウドへ送る ③ GitHub クラウド / コードを保管・共有する ④ Supabase クラウド / 会員情報や投稿データを持つ ⑤ Netlify クラウド / Webサイトを公開する

担当

役割 やること 主に出てくる工程
案件オーナー 期限、費用、お客様への公式な返事 03 / 05 / 06
営業 話を聞いて、受けるかを判断する 01

少人数なら1人が兼ねてよいです。兼ねるときほど、決まったことを紙に残します。

迷ったとき

  • お客様が急いでいる → 工程は飛ばさず、範囲を小さくする。01 の「案件の大きさ」を見る。
  • 「ついでにこれも」と言われた → 04 の「変更の締め切り」で、今回やる / 次に送る / やらない に分ける。
  • 終わりが見えない → 02 の「完了定義」が書けているか戻って確かめる。
