始め方

営業が作った GitHub を引き継ぐ。空のリポジトリは作らない。クローンして Cursor で開き、機能一覧・前提・やらないことを読んでから書く。分からない範囲は想像で埋めず、営業へ返す。

お客様にとって開発は投資です。2〜3か月遅れると、回収の開始も遅れます。

初稿の出し方

デザインが全部決まるのを待たない。中身から先に作り、初稿 → 修正 → 検収で確定させる。

いつ使う 注意
モックアップ 画面が多い、使い方を想像しにくい 見た目だけ。先に「保存はできません」と言う
機能一覧だけ 既存画面の直し、権限やデータが主 02の一覧を一緒に読む。割れた画面だけモックにする

言葉がずれるので、社内ではこう使う。ワイヤーフレーム＝灰色の骨格。プロトタイプ＝画面遷移がある。モックアップ＝見た目に近い試作（近年は基本こちら）。

定例（2週に1回）

見せる → 決める → 次までの宿題、で終わる。記録は、やった人がその日のうちに Markdown でリポジトリへ置く。ドライブだけに置かない。

段階 ここで確定させる
初稿 デザイン、レイアウト、リンク、色、フォント、動きの有無
修正 不具合、崩れ、文言、画像、動きの大枠
検収 残りの不具合と動き。お客様が操作して判定する

「これも入れて」が来たとき

その場で「やります」「タダでできます」と言わない。Cursor ですぐ作れることと、契約の範囲は別です。

今回の範囲 追加の費用
誤字、色、並び、表示崩れ、動かない不具合 新しい画面、権限、保存、帳票、外部連携、約束に無い業務

返すのはこれだけ。「持ち帰って、やる / 次に送る / 別途見積 で戻します。」「前回言ったはず」には、要件定義の版を指す。「A・B・Cまで」なら D は入っていない。入れるなら見積と、いつやるかも決める。

迷ったらその場で決めず、営業か案件オーナーへ。やり取りの実画面は3パターン、あとで足す。

締め切り

  • リリースの1か月半前まで（小さい案件は2週間前）。以降は次へ送る。
  • 返事の前に、範囲・日数・費用を出す。
  • 今回やる / 次に送る / やらない、を決めた日を残す。

キックオフで先に伝える。あとから言うと「間に合わないのは当社の都合」になる。

基盤の話が出たとき

「AWSで」でもすぐ従わない。会員・ログイン・表データなら Supabase の方が速いことが多い。希望は聞いたうえで、速さ・運用・費用を比べて提案する。

使うツール

操作は各ページ。全体の流れだけ先に見る。

① Cursor ローカル / コードを書く・編集する ② GitHub Desktop ローカル / 変更を保存してクラウドへ送る ③ GitHub クラウド / コードを保管・共有する ④ Supabase クラウド / 会員情報や投稿データを持つ ⑤ Netlify クラウド / Webサイトを公開する

検収

  • 完了定義を、お客様が操作して確認する。
  • 合格 / 残件つき合格 / 不合格。仕事が止まるものだけ不合格。
  • 約束に無い「もっとこうしたい」は見積に回し、判定に混ぜない。

  • 定例の記録が、リポジトリに残っている
  • 追加要望が、今回 / 次 / 別途見積 に分かれている
  • 合格、または本番を止めない残件つき合格
