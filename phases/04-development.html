PHASE 04

開発・検証

段階的に実装し、関係者レビューと現場検証を挟みながら品質を高めます。仕様変更は影響と優先度を明示して扱います。

担当実装リード
入口初稿提出
出口動作テスト・検収
定例2週に1回

進め方

デザインが全部決まるのを待ちません。認証・権限管理・管理画面は内部ライブラリがあるので、中身から先に作れます。デザインと開発を同時に進めて、初稿 → 修正 → テストの順に確定させていきます。

段階 ここで確定させるもの
初稿提出 デザイン、レイアウト構成、リンク先、カラー、フォント、アニメーション・エフェクトの有無
修正・改善 不具合、表示崩れ、文言や改行、画像の差し替え、動きの大枠
動作テスト・検収 残りの不具合、アニメーション・エフェクトの動き

2週に1回、先方と定例を組みます。見せる → 決める → 次までの宿題を確認する。資料・議事録・仕様書・操作方法は見えるところに置き、認識のずれで後戻りしないようにします。

初稿の出し方

案件によって、モックアップを作る場合と、機能一覧だけで進める場合があります。

モックアップを作る

Cursorで画面だけ先に作り、お客様に触ってもらいます。

  • 画面の数が多い、現場の人が使い方を想像しにくいとき
  • 並び順やボタンの位置で意見が割れそうなとき
  • 中身は動かなくてよい。見た目と流れだけ

機能一覧だけで進める

02で作った機能一覧のページを、一緒に読みます。

  • 既にある画面の直し、業務がはっきりしているとき
  • データの正しさや権限が主で、見た目の判断が少ないとき
  • 迷ったらこちらから始め、意見が割れた画面だけモックを作る

モックアップは確認のための試作です。お客様が「もう出来ている」と受け取らないよう、「見た目だけで、保存はできません」と先に言います。

使うツール

開発から公開までに5つのツールを使います。ローカル（自分のPC内）とクラウドに分けて覚えると迷いません。各ツールの使い方は、それぞれのページにまとめています。

① Cursor ローカル / コードを書く・編集する ② GitHub Desktop ローカル / 変更を保存してクラウドへ送る ③ GitHub クラウド / コードを保管・共有する ④ Supabase クラウド / 会員情報や投稿データを持つ ⑤ Netlify クラウド / Webサイトを公開する

お客様に説明するときは、ツール名より役割で伝えます。「作る場所」「置く場所」「見せる場所」の3つに分けると、初めての方でも1回で理解できます。

変更の締め切り

  • 修正・変更は、リリース日から逆算して1か月半前までにもらう。それ以降は次のリリースに送る。
  • 返事の前に、影響（範囲 / 日数 / 金額）を伝える。
  • 「今回やる / 次に送る / やらない」のどれかにして、決めた日を残す。

1か月半は、リリース日が決まっている案件の目安です。2週間〜1か月で終わる小さい案件は、リリースの2週間前までにします。どちらもキックオフMTGで伝えます。あとから言うと「間に合わないのは当社の都合」になります。

出口：動作テスト・検収

  • 完了定義を1つずつ、お客様が操作して確認する。
  • 判定は「合格 / 残件つき合格 / 不合格」。仕事が止まるものだけ不合格にする。
  • 約束に無い「もっとこうしたい」は、別途見積として改めてご相談します。検収の判定には混ぜない。

次に進む合図

  • 初稿でデザインが確定し、定例の記録が残っている
  • 合格、または本番を止めない残件つき合格になっている
  • 受けた変更が、要件定義書の最新版に入っている
