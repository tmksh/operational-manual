Supabase

ひとことで言うと

Supabaseは「Webサイト本体」ではなく「裏側のデータ管理」です。お店に例えると、Webサイトは店頭、Supabaseは奥の倉庫です。

見る人 お客様のスマホ・PC ページを開く
→
店頭 Webサイト Netlifyが配る画面
⇄データを
取りに行く
奥の倉庫 Supabase データ・ログイン・ファイル

Cursorでコードを直しても、Supabaseの中のデータは変わりません。逆に、Supabaseのデータを直してもコードは変わりません。別々に扱います。

Supabaseでできること

裏側に必要なものが、1つにまとまっています。うちの案件でよく使うのは上の3つです。

会員・予約・投稿などを表で保存

例：予約一覧、帳票の元データ
よく使う Authentication ログイン

会員登録・ログイン・パスワード再設定

例：決済、メール送信、外部連携

値 中身の例 たとえ
Project URL https://xxxx.supabase.co 住所

Supabaseの画面上部の Connect を押すと、両方まとめて出ます。Project Settings の API Keys からも見られます。

キーは2種類。片方は絶対に画面に入れない

anon / publishable key

合鍵。画面のコードに入れてよい。RLSで許された部屋しか開かない。

service_role / secret key

マスターキー。RLSを無視して全部開く。画面のコード・GitHub・NEXT_PUBLIC_ や VITE_ 付きの変数には入れない。

キーの置き場所（ローカルと本番）

結論

ローカルは .env.local、本番は Netlify の環境変数。.env.production は作りません。

自分のPC（Cursor） ローカル
  • src/ など
  • .env.local
→プッシュ
GitHub クラウドの保管
  • src/ など
  • .env.local（届かない）
→ビルド
Netlify 本番
  • src/ など
  • 環境変数（画面で入れる）

.env.local はGitHubに上げません（.gitignore で止めます）。NetlifyはGitHubのファイルからサイトを作るので、.env.local は届きません。だから同じ値を、Netlifyの画面にも入れます。

ローカル：.env.local

プロジェクトのいちばん上の階層に作ります。

.env.localNEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...

書き換えたら、npm run dev を止めて起動し直します。

本番：Netlifyの環境変数

  1. Site configuration → Environment variables
  2. Add a variable で、名前と値を .env.local と同じに入れる
  3. Deploys → Trigger deploy で作り直す

入れただけでは反映されません。作り直して初めて効きます。

変数の名前

頭につく文字は、作り方で決まっています。頭の文字は「画面に出してよい」という印です。

作り方 住所（URL） 合鍵（anon key）
Next.js NEXT_PUBLIC_SUPABASE_URL NEXT_PUBLIC_SUPABASE_ANON_KEY
Vite（React など） VITE_SUPABASE_URL VITE_SUPABASE_ANON_KEY

つなぐ設定は、Cursorに頼む

Cursorのチャットへ

Supabaseにつなぐ設定をして。URLとanonキーは .env.local から読むようにして、.env.local は .gitignore に入れて。

できあがると、次のような「つなぎのファイル」が1つできます。中身を覚える必要はありません。

lib/supabase.ts（例）import { createClient } from '@supabase/supabase-js'

export const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!
)

RLS（見ていい人を決める鍵）

RLS（Row Level Security）は、データベース側でかける権限です。「誰が、どの行を、見る・足す・直す・消すことができるか」を決めます。

家に例えると

家の中で、兄弟ごとの部屋に鍵をつけて、それぞれに自分の部屋の鍵だけを持たせる感じです。部屋の中身がデータです。

たとえ Supabaseでは
家 表（会員の表、予約の表など）
部屋 行（1人分・1件分のデータ）
鍵を持っている人 ログインしている人
鍵のルール RLSのルール（ポリシー）。例：「自分の行だけ見てよい」

鍵は4種類ある

同じ部屋でも「見るのはいいけど、消すのはダメ」のように分けられます。

見る例：自分の予約だけ
足す例：ログインした人だけ
直す例：自分のプロフィールだけ
消す例：管理者だけ

よくある2つの失敗

RLSをつけ忘れる

鍵のない家です。画面には合鍵（anon key）が入っているので、その気になれば誰でも全部の部屋に入れます。他の会員の情報まで見えてしまいます。

RLSはオン、ルールがない

鍵はかけたのに、誰にも鍵を渡していない状態です。本人も入れないので、画面にデータが1件も出ません。

ルールはCursorのチャットへ

membersの表にRLSをつけて、ログインした本人の行だけ、見る・直すができるようにして。

SQL（データベースへの命令文）

SQLは、データベースに「これをやって」と頼む言葉です。Supabaseの SQL Editor に貼って Run を押すと動きます。自分で書かなくても、Cursorに書いてもらえば大丈夫です。

Table Editor（マウスで）

1件ずつ見る・直す。Excelと同じ感覚。

例：1人の電話番号を直す

SQL Editor（命令文で）

表を作る、列を足す、RLSのルール、まとめて直す、集計。

例：予約の表を新しく作る

どんなときに使うか

やりたいこと SQLの例 意味
見る select * from members; 会員を全部見る
表を作る create table reservations (...); 予約の表を作る
列を足す alter table members add column phone text; 電話番号の列を足す
直す update members set plan = 'pro' where id = 2; 2番の人だけ直す
RLSのルール create policy ... using (auth.uid() = user_id); 本人だけ見られる

SQLを流すときの順番

① Cursorに頼む「〇〇する SQL を書いて」
② 検証環境で Run本番ではなく、試し用のプロジェクトで
③ 画面で確認データや表示がおかしくないか
④ 本番で Run実装リードの確認を取ってから

where を忘れない

update と delete は、where（どの行か）をつけないと全部の行が変わる・消えます。本番は戻せません。

SQLはファイルで残す

流したSQLは、リポジトリの supabase/ フォルダに保存します。あとから何をしたか追えます。

触るときの決まりごと

場面 やること
本番データを直す 実装リードの確認を取ってから。1人で判断しないコードと違い、消したら履歴から戻せません
列や表を増やす 先に検証環境で試す。本番に直接入れない
お客様に画面を見せる 他のお客様のデータが映り込んでいないか確認する
キーを扱う コードに直書きしない。ローカルは .env.local、本番は Netlify の環境変数

GitHubは間違えても履歴から戻せますが、Supabaseの本番データは戻せません。この2つは危なさの種類が違う、と覚えてください。

お客様への説明例

こう言う

  • 「サイトで使うデータを保管している場所です」
  • 「会員情報や投稿内容はここに入っています」
  • 「見た目とは別に、データだけを管理しています」

避ける言い方

  • 「BaaSでPostgreSQLが…」（伝わりません）
  • 「サイトが入っている場所です」（Netlifyと混ざります）
  • 「無料なので大丈夫です」（件数が増えると有料です）

困ったとき

起きたこと どうするか
ログインできない Authentication にそのユーザーが登録されているか見る
データが画面に出ない（0件） Table Editor に行があるか → RLS のルールで止まっていないか
ローカルでは出るのに、本番だけ出ない Netlify の環境変数を入れたか → 入れたあと Trigger deploy したか
.env.local を直したのに変わらない npm run dev を止めて起動し直す
Invalid API key と出る キーの貼り間違い。前後に空白や改行が入っていないか見る

英語のエラーは、そのままCursorのチャットに貼って「直して」で大丈夫です。

次に進む合図

  • 本番データを直す前に、実装リードの確認を取った
  • .env.local をGitHubに上げていない
  • service_role（secret）キーを画面のコードに入れていない
  • 新しく作った表に、RLSをつけた
  • お客様に見せる画面に、他社のデータが映っていない
